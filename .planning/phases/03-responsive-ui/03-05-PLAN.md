<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| game state → assistive technology | The live region reads game state aloud, including a player-supplied display name |
| modal open → page behind | A dialog claiming to be modal must actually prevent keyboard interaction with the board behind it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-02 | Tampering | celebration dialog focus containment | mitigate | `useFocusTrap` wraps Tab and Shift+Tab with explicit `preventDefault()` and manual `.focus()` calls at both ends; Task 2 test 5 asserts focus never lands on a board element while the dialog is open. Without this, a keyboard user could act on the board through a dialog the UI presents as blocking |
| T-03-03 | Information Disclosure | turn announcer text | mitigate | The live region emits exactly two contracted strings — `Your turn` and `<Name>'s turn` — with no board-state summary (D-05). An acceptance criterion pins the string count, so the announcer cannot grow into a channel that reads out state the visual UI does not show (for example another player's hand) |
| T-03-05 | Injection | player name in the live region | mitigate | The name is rendered as a React text child of the live-region `div`, never via `dangerouslySetInnerHTML` and never concatenated into an attribute value, so React's escaping applies. Player names already reach the DOM through the header readout and lobby list under the same treatment |
| T-03-06 | Denial of Service | document-level keydown listener | mitigate | The trap is active only while `celebrationModal?.show === true`; `useFocusTrap`'s cleanup removes the listener, so a dismissed modal cannot keep swallowing Escape or Tab for the rest of the session |
| T-03-SC | Tampering | npm installs | accept | No packages installed; 03-RESEARCH.md records zero new dependencies for the phase |
</threat_model>

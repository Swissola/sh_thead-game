Create `src/hooks/useTurnTimeoutSweep.ts` exporting
`useTurnTimeoutSweep({ roomCode, testMode, phase, turnStartedAt, currentTurnPlayerId, playerId })`
returning `{ graceExpired: boolean }`, plus `export const TURN_SWEEP_INTERVAL_MS = 5000`.

This hook is the missing Browser/Client half of RESEARCH.md's Architectural Responsibility Map
row for D-05. Plan 02-07 built `check-turn-timeout` and tested it thoroughly, but nothing calls
it — so as things stand a stalled turn never resolves and the whole grace-period design is
unreachable. This is the trigger.

Keep the local clock strictly a hint. The request body carries `roomCode` and nothing else: no
timestamp, no elapsed count, no "the grace period has expired" assertion. `checkTurnTimeout`
recomputes elapsed time from the stored `turn_started_at` against its own `store.now()` and
returns `TIMEOUT_NOT_ELAPSED` with zero writes if the client was early (T-02-24). A client that
lies about its clock achieves exactly nothing, which is why any authenticated player in the room
may call this.

Do not trigger on your own turn. A player sitting on their own turn is present and can act, and
a client that times itself out would be self-sabotage; every other client is still sweeping, so
the turn resolves regardless as long as one other player is connected. This is also why the hook
runs on every client rather than being elected to one: no coordination, and the not-elapsed path
costs a single server-side read.

Keep the cadence local. `TURN_SWEEP_INTERVAL_MS` is a purely client-side display/polling
concern with no server counterpart, so it belongs in this file rather than in
`src/supabase/roomTypes.ts`'s shared contract. 5s means the badge flips and the auto-pickup
lands within five seconds of expiry, which is comfortably inside the human tolerance for a
60-second grace period.

Guard against pile-up with an in-flight `useRef` boolean rather than cancelling — a pending call
that is slow should not spawn a second, and a failed one should simply be retried on the next
tick without a toast. A missed sweep is not a user-facing error and the next tick corrects it,
exactly as `usePresence` treats a missed heartbeat.

Follow `usePresence.ts`'s hook shape throughout: `useState` for `graceExpired`, `useRef` for the
interval handle and the in-flight flag, one `useEffect` with the same short-circuit-then-arm-then-
cleanup structure, returning a small plain object.

Then wire it into `GameScreen.tsx`: call the hook with the room code, test mode,
`gameState.phase`, the context's `turnStartedAt`, `gameState.players[gameState.currentTurn]?.id`
and `playerId`. Use its `graceExpired` together with Task 1's `isOffline` and the existing
`isTheirTurn` to upgrade the badge to D-10 state 2 — when a player is offline **and** it is their
turn **and** the grace period has expired, the badge becomes "Offline - auto-picking up" with a
`RotateCw` icon in amber (UI-SPEC's amber "the system automatically changed something" colour,
the same one plan 02-02 gave the reconciliation toast). Per UI-SPEC's Interaction Notes this is
a replace-in-place on the same badge element — swap text, icon and colour classes, do not render
a second badge.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| other browsers' Presence reports → this player's board | Self-reported connectivity, rendered as a badge |
| local clock → `check-turn-timeout` request | The browser decides *when* to ask, never *whether* the period elapsed |
| game board UI → menu | Leaving must not be a way to affect anyone else's state |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-41 | Spoofing | A client falsely reporting another player absent, greying out their tile | accept | Same acceptance as T-02-30: Presence drives display only. No rules decision reads it — D-05's timeout uses the server clock, D-06's seat matching and D-08's host transfer use the server-written `player_seen`. The worst outcome is a cosmetically wrong badge |
| T-02-42 | Tampering | A modified client asserting the grace period has elapsed early to force another player's pickup | mitigate | The request body carries only `roomCode`, asserted by a test on the invoke argument; plan 02-07's `checkTurnTimeout` recomputes elapsed time from `store.now()` and returns `TIMEOUT_NOT_ELAPSED` with zero writes when the caller is early (T-02-24) |
| T-02-43 | Denial of Service | Every client sweeping a hot room in parallel | mitigate | One in-flight call per client, a 5s cadence, the current-turn player never triggers at all, and the not-elapsed server path returns before any write (T-02-27). Write contention is additionally bounded by `MAX_WRITE_ATTEMPTS` |
| T-02-44 | Elevation of Privilege | Leave Game used to remove a seat, or another player's seat | mitigate | The handler only calls the context's local `setGameState(null)`; an acceptance criterion asserts zero `functions.invoke` calls on leave. Seats are removed in exactly one place in this phase — host-gated, lobby-only `remove-player` (D-07, plan 02-07) |
| T-02-45 | Information Disclosure | The offline badge revealing who is at the table when | accept | The badge conveys only what any player at a shared room code can already observe from whose turn stalls; the room contains card positions in a party game (same posture as T-02-08) |
</threat_model>

<objective>
Close the major gap from `02-UAT.md` test 3: routine connectivity bookkeeping pollutes the
game-state version stream. `heartbeat()` (every ~15s, from every connected player) and
`joinRoom()`'s `'existing'`-seat auto-rejoin branch (D-01) both write through
`withVersionRetry`, which unconditionally increments `version` on every successful write - even
though neither changes `state` outside the rare lobby host-transfer case. Each such write
broadcasts a version-bumped, content-unchanged row to every subscriber, and
`useRoomSubscription`'s reconciliation check compares that against the client's own *in-flight
optimistic display*. A heartbeat landing mid-move therefore looks exactly like "the server
disagreed". Live evidence from 02-13 Task 3: a "Ready to Play" press producing a spurious
invalid-move-adjacent popup, and a legal 7-play producing a false "Your move didn't stick" toast.

Purpose: MPLAY-05's optimistic-then-reconcile contract is only meaningful if a reconciliation
signal means something. Right now it fires on ambient traffic, which trains players to ignore it
and makes a real reconciliation indistinguishable from noise. MPLAY-02's Realtime stream, D-01's
auto-rejoin (MPLAY-03), the join path (MPLAY-01) and the connectivity signal (MPLAY-06) are all
implicated in the same write path.
Output: a version-exempt, concurrency-safe `player_seen` write path used by both callers, with
the full CAS path retained for the one case that genuinely mutates state.
</objective>

Two properties of that statement are the whole point of this task, and both must be documented
in the migration's header comment so a future reader does not "simplify" them away:

  1. **`version` is deliberately absent from the SET list.** That is what makes the write
     version-exempt. Clients already discard same-version Realtime deliveries via
     `useRoomSubscription`'s `if (version <= lastAppliedVersionRef.current) return;` filter
     (T-02-29), so no client-side change is needed anywhere - the broadcast still goes out, it
     is simply dropped before it can reach the reconciliation comparison that produced the
     false "your move didn't stick" toasts.
  2. **The `||` merge is evaluated server-side under the row lock, which is what keeps it safe
     under concurrent writers.** A read-then-write from the Edge Function would not be: two
     heartbeats (D-03 same-identity multi-tab, or two different players beating close together)
     would each read the same `player_seen`, merge only their own key, and the second write
     would silently clobber the first - a lost update. Conditioning the write on the current
     `version` does not help either, because neither writer changes `version`, so both CAS
     predicates still match. Under READ COMMITTED, the second `UPDATE` blocks on the row lock,
     then re-evaluates `player_seen || ...` against the freshly committed value, so both merges
     survive. Do not replace this with a PostgREST read-then-write.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted client → `heartbeat` / `join-room` | A caller may try to write another player's last-seen entry, or to reach the new SQL function directly |
| Edge Function → Postgres `rooms` row | Concurrent writers on the same row; the merge must not lose an update |
| Postgres → Realtime subscribers | Every UPDATE broadcasts; what the version says about that broadcast is what clients act on |

  <action>
Record the decision first, in `.planning/phases/02-real-cross-device-multiplayer/02-VALIDATION.md`:
tick the Wave 0 item "Decide and set up Edge Function test strategy" and add a one-line note naming
the choice — **scripted `supabase functions serve` + `fetch`, run via `npm run test:edge:smoke`** —
over the Deno test runner. Three reasons, and they are worth stating because the alternative is
superficially the more obvious one:
  - The Supabase CLI already bundles the Deno runtime, so serving costs no new toolchain
    dependency. RESEARCH.md's Environment Availability table lists Docker and Node, not a
    standalone Deno.
  - The wrappers' entire load-bearing behaviour is `withSupabase({ auth: 'user' })` validating a
    real JWT. A `deno test` that imported `index.ts` would have to stub that out, which would test
    everything except the thing worth testing.
  - It matches the existing `scripts/check-edge-wrappers.mjs` convention — a plain Node `.mjs`
    script with per-case PASS lines and a non-zero exit — so the two read as one family.

Create `scripts/smoke-edge-functions.mjs`:

  - **Preflight.** Shell out to `npx supabase status`. If the local stack is not running, exit
    non-zero with a message telling the operator to run `npm run supabase:start`. Never skip
    silently and exit 0 — a smoke suite that passes by not running is worse than no smoke suite.
  - **Target the local stack, not `.env.local`.** Parse the API URL and the publishable/anon key
    out of the `supabase status` output rather than reading `.env.local`. After plan 02-03's
    checkpoint `.env.local` points at the **hosted** project, and this script writes rooms,
    plays moves and removes players — it must never do that against the hosted database.
  - **Serve.** Spawn `npx supabase functions serve` as a child process. Poll the functions
    endpoint until it answers anything at all rather than refusing the connection, bounded at
    around 120 seconds, then proceed. Register teardown on normal exit, on thrown failure and on
    `SIGINT`, so a failed run never leaves an orphaned serve process holding the port.
  - **Identity.** Create two independent `@supabase/supabase-js` clients against the local URL
    with `persistSession: false` and call `signInAnonymously()` on each, giving two genuinely
    distinct `auth.uid()` values — real players A and B, not two names for one subject. Keep both
    `session.access_token` values.
  - **`callFunction(name, token, body)`** helper: POST to `${functionsUrl}/${name}` with
    `Authorization: Bearer <token>` and the `apikey` header, returning `{ status, json }`. A
    `null` token omits the Authorization header entirely.
  - **`check(label, condition)`** helper printing `PASS <label>` / `FAIL <label>`, accumulating
    failures and exiting non-zero if any accumulated.

Then the authentication and identity cases, which are the ones no static check can reach:
  1. `create-room` with no Authorization header returns HTTP 401 and `error.code` `UNAUTHENTICATED`
  2. `create-room` with a syntactically valid but bogus bearer token also returns 401
  3. `create-room` called by A with a body that *also* carries `playerId` set to B's uid produces
     a room whose `state.host` is **A** — the runtime proof of T-02-13's JWT-subject override,
     which `check-edge-wrappers.mjs` can only prove by grep
  4. `apply-move` called by B, with a body whose `move.playerId` claims to be A, is rejected and
     leaves the room's `version` unchanged — MPLAY-04's headline claim, demonstrated rather than
     asserted
  5. a malformed (non-JSON) body returns HTTP 400 and `error.code` `BAD_REQUEST`

Add the npm script `test:edge:smoke` → `node scripts/smoke-edge-functions.mjs`.

Note the runtime honestly in the script's header comment: a first run pulls and starts the
functions container and can take a few minutes, well beyond the usual fast-feedback target. This
is the same accepted one-time bootstrap exception as plan 02-01's `supabase start`; warm runs are
tens of seconds. That cost is why this suite is a wave-6 gate rather than a per-commit check —
the per-commit signal stays Vitest plus `check-edge-wrappers.mjs`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| smoke script → served Edge Functions | The script deliberately plays the part of a hostile client |
| smoke script → database | The suite writes real rooms, moves and removals |
| child `supabase functions serve` process → developer machine | A spawned server holding a port |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-46 | Tampering | Smoke suite writing to the hosted production project | mitigate | The target URL and key are parsed from `npx supabase status`, never from `.env.local` (which points at the hosted project after plan 02-03's checkpoint); an acceptance criterion greps for zero `.env.local` references in the script |
| T-02-47 | Repudiation | A smoke run that passes by silently skipping | mitigate | A stopped local stack is a non-zero exit with an explicit message, never a skip; an acceptance criterion requires verifying that failure path by actually running with the stack down |
| T-02-48 | Denial of Service | An orphaned `functions serve` child process holding the port after a failed run | mitigate | Teardown registered on normal exit, thrown failure and `SIGINT`, with an acceptance criterion that verifies no process survives a mid-run kill |
| T-02-49 | Information Disclosure | Anonymous session tokens minted by the script | accept | They are short-lived local-stack anonymous tokens against a throwaway Docker database, printed nowhere and discarded at process exit |
</threat_model>

game (`start-game`) and applying every in-game move (`apply-move`). Both call the exact

here too (RESEARCH.md Pitfall 3).

an explicit cheating-client test group.

Create `supabase/functions/_shared/applyRoomMove.ts` exporting
`applyRoomMove(store, input: { playerId; roomCode; move: unknown })`.

Validate the move shape first: reject anything whose `type` is outside the four-member `Move`
union with `BAD_REQUEST` before the engine sees it (ASVS V5 — the engine assumes a well-formed
union member).

Then set `playerId` on a copy of the move to `input.playerId`, the verified JWT subject supplied
by the wrapper. Never trust the payload's own field, and do not mutate the caller's object.
This is the control that makes MPLAY-04 real: `applyMove` verifies that the *named* player owns
the turn, but has no way to know who actually sent the request.

Run the read/apply/write cycle through `withVersionRetry`, calling `applyMove` from
`./engine.ts` on each attempt so a retry re-derives from the winning state rather than replaying
a stale computation. Return engine errors verbatim so the client's toast copy and the closed
`ERROR_CODES` set stay consistent across both tiers.

resolves RESEARCH.md's Open Question 1 / Pitfall 4: `applyPlayCards` can leave `currentTurn`
unchanged after a burn, and from the player's point of view that is a fresh decision point
deserving a fresh grace period. It is also simpler and cannot strand a player mid-burn-sequence
with an expired clock. Record this choice in a code comment citing Pitfall 4.

Append an audit row via `store.appendMove` after each successful write, carrying the caller's
id, the move as applied (after the override) and the resulting version — this is what makes a
D-11 reconciliation incident reconstructable after the fact.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted client → `apply-move` HTTP | Every field of the move payload is attacker-controlled |
| untrusted client → `start-game` HTTP | Caller may not be the host, or the room may already be dealt |
| Edge Function → `rooms` / `moves` tables | Service-role write, RLS bypassed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-18 | Spoofing | `move.playerId` | mitigate | `applyRoomMove` overwrites it with the verified JWT subject before calling `applyMove`; tested by the cheating-client case asserting `NOT_YOUR_TURN` |
| T-02-19 | Tampering | Client-side deck rigging via a fabricated dealt state | mitigate | `start-game` deals server-side with `GameLogic.shuffleDeck(GameLogic.createDeck(n))`; RLS means a client-fabricated dealt state has no write path at all |
| T-02-20 | Elevation of Privilege | Non-host starting the game | mitigate | `startGame` rejects with `NOT_HOST` when the caller is not `state.host`; the client-side guard is treated as an affordance, not a control |
| T-02-21 | Tampering | Duplicate or replayed move submission | mitigate | The `version`-conditional update makes a stale retry a no-op — its expected version no longer matches, so it is re-derived against current state rather than double-applied |
| T-02-22 | Input Validation | Malformed move payload reaching the engine | mitigate | Move `type` validated against the four-member union with `BAD_REQUEST` before `applyMove` is called |
| T-02-23 | Denial of Service | Unbounded retry loop on a hot room | mitigate | `MAX_WRITE_ATTEMPTS = 3` then `CONFLICT`, so a contended room returns quickly instead of spinning |
</threat_model>

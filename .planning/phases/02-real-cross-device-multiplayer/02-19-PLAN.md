<objective>
Close the two gaps 02-18 deliberately left open for MPLAY-07 ("The room host can set the turn
auto-pickup timeout ... adjustable in the lobby before the game starts and visible to all
players, not just the host"): 02-18 built the full server-authority half (a validated
`SET_TURN_TIMEOUT` move, `GameState.turnTimeoutMs`, bounds enforced in `applyMove`, and
`checkTurnTimeout` honouring the configured value) but left it reachable only by dispatching the
move programmatically - nothing in the UI could reach it, and the client-side trigger that makes
`check-turn-timeout` reachable at all (`useTurnTimeoutSweep`) still compared elapsed time against
the hardcoded `TURN_GRACE_MS` constant regardless of what a room's `turnTimeoutMs` was actually set
to.

This plan is UI/wiring-only - it adds no new engine rule, no new Edge Function, and no new
validation. Every constraint (host-only, lobby-phase-only, `[30000, 300000]`ms bounds) is already
enforced server-side by 02-18's `applySetTurnTimeout`; this plan's own host-gating in
`LobbyScreen.tsx` and its preset-bounded `<select>` are presentation-layer defense-in-depth,
exactly like the pre-existing `isHost` gating around Start Game and `removePlayerFromLobby` in the
same file, not a new authorisation boundary.

Design decisions settled in this session's Socratic exploration (not re-derived here): controller
is `state.host` only, no new permission concept; the control is only editable while
`state.phase === 'lobby'` - satisfied structurally, since `App.tsx`'s `Router` only ever mounts
`LobbyScreen` while `gameState?.phase === 'lobby'` (confirmed by reading `Router`'s own
`{gameState?.phase === 'lobby' && <LobbyScreen ... />}` line), so no second phase check is needed
inside the component itself; range is 30s-300s inclusive; default is 60s; every player in the
lobby sees the current value, only the host can change it.

Purpose: without this plan, MPLAY-07 remains server-capable but practically unreachable - a real
player has no way to ever set a non-default timeout, and a room that somehow did have one set
(e.g. via a future admin tool) would still auto-pick-up at the wrong moment on the client side,
because `useTurnTimeoutSweep` would keep triggering `check-turn-timeout` at the old fixed 60s mark
regardless of the room's actual configured value.

Output: a lobby control any player can see and only the host can change, wired through the same
`dispatchMove` seam every other move already uses; and a `useTurnTimeoutSweep` that reads the
room's own `turnTimeoutMs` instead of a fixed constant, so the visible "Offline - auto-picking up"
badge state (D-10 state 2, `GameScreen.tsx`) and the `check-turn-timeout` calls it triggers both
line up with whatever the host actually configured. This closes MPLAY-07 end-to-end.
</objective>

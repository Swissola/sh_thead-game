Create `supabase/functions/_shared/heartbeat.ts` exporting
`heartbeat(store, input: { playerId; roomCode })` and the pure helper
`transferHostIfStale(state, playerSeen, nowMs)`.

This is the server's own connectivity signal, and the reason Realtime Presence cannot be used
for it: Presence lives in the Realtime cluster's memory, is reported by the client, and is not
readable or trustable inside an Edge Function. `player_seen` is written only with `store.now()`,
so "connected" means "the server saw a request from this player recently", which is
unforgeable in the way that matters.

`heartbeat` refreshes only the caller's entry. Clients call it on a `HEARTBEAT_INTERVAL_MS`
(15s) cadence; `DISCONNECT_THRESHOLD_MS` (45s) allows three missed beats before a player counts
as disconnected, which is the same threshold `joinRoom`'s `resolveSeat` uses for D-06. Note that
plan 02-12's D-10 badges are driven by Realtime Presence, not by this threshold — the two signals
are deliberately separate (plan 02-08's T-02-30), and this one exists so the server never has to
trust a client's self-report.

Fold D-08's host transfer into the same write rather than adding a scheduled job: every
heartbeat runs `transferHostIfStale` first, so a lobby whose host has dropped recovers as soon
as any remaining player beats. Restrict it to the lobby phase — per D-08 the host has no
mid-game powers, so transferring mid-game would be churn with no benefit and would confuse the
`Crown` badge. Pick the earliest-seated currently-connected player for determinism, so two
simultaneous heartbeats cannot disagree about who the new host is.

Do not touch `turn_started_at` here. A player who is connected but simply not acting must still
time out per D-05; coupling the two would let an idle-but-online player stall the table forever.

Create `src/__tests__/edge/heartbeat.test.ts` covering all seven behaviours, with
`transferHostIfStale` tested directly across the phase matrix.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted client → `check-turn-timeout` | Caller may be trying to force another player's turn to expire early |
| untrusted client → `heartbeat` | Caller may be trying to mark someone else connected or disconnected |
| untrusted client → `remove-player` | Caller may not be the host, or may target the wrong seat |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-24 | Tampering | Forcing an early turn timeout | mitigate | Elapsed time is recomputed server-side from the stored `turn_started_at` against `store.now()`; no caller-supplied timestamp is read, and a not-yet-elapsed call returns `TIMEOUT_NOT_ELAPSED` with zero writes |
| T-02-25 | Spoofing | Marking another player connected or disconnected | mitigate | `heartbeat` writes only `player_seen[ctx.userClaims.sub]`, never an id from the body; a test asserts other entries are byte-identical after a beat |
| T-02-26 | Elevation of Privilege | Non-host removing a player, or removing a mid-game seat | mitigate | `removePlayer` requires `caller === state.host`, requires `phase === 'lobby'`, and refuses to target the host; mid-game seats remain protected by D-04 |
| T-02-27 | Denial of Service | Repeated timeout-check spam on a hot room | mitigate | The not-elapsed path returns before any write, so spam costs one read; the write path is additionally bounded by `MAX_WRITE_ATTEMPTS` |
| T-02-28 | Denial of Service | A room stalled because every player is offline | accept | The lazy client-triggered sweep only resolves once someone reconnects (RESEARCH.md Assumption A2). Acceptable under D-14, which lets any player leave at will, so no one is ever trapped. `pg_cron` + `pg_net` is the documented escalation if this proves annoying in practice |
</threat_model>

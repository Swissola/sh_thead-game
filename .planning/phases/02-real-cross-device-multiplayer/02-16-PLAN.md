<objective>
Close the major gap from `02-UAT.md` test 7: `useRoomSubscription`'s `handlePayload` fires
`onReconciled()` (the "Your move didn't stick" toast, via `GameContext.tsx`'s `notifyReconciled`)
whenever an incoming broadcast's state differs from `localStateRef.current`, with no check for
whether the comparing client actually has a move of its own outstanding. For any client that did
not just submit a move, local state is - by construction - the pre-move snapshot right up until
the broadcast delivers the post-move state, so the comparison is structurally guaranteed to
mismatch on essentially every real move any other player makes. Confirmed live: a PC that made no
move got the toast immediately after a phone (a different player) made a legitimate, successful
move, during both setup phase and normal play.

This is distinct from the two 02-14/02-15 gaps: those were about *ambient, no-op* writes
(heartbeats, D-01 auto-rejoin, an empty-pile stall) bumping the version with unchanged content.
This one fires on completely legitimate, content-changing writes too, and specifically for the
client who did *not* make the move - `useGameState.ts`'s own `result?.error` branch already
raises the correctly-scoped toast for a genuine server-side rejection of *this* client's own move
(D-11/D-12); that path is not the bug and is not touched here.

Purpose: MPLAY-05's optimistic-then-reconcile contract (D-11) is only meaningful if the
reconciliation signal means something. Right now it fires on ambient opponent traffic, training
players to ignore a toast that is supposed to mean "the system corrected something for you
specifically." MPLAY-02's Realtime stream is the delivery mechanism this fix gates.

Output: a per-client "pending move" tracker in `GameContext.tsx`, set the instant a real (non-test
mode) move submission fires and resolved on the first of three definite outcomes - a broadcast, a
definite submission failure, or a bounded timeout - consulted by `useRoomSubscription` before it
ever calls `onReconciled`. `onServerRoom`'s unconditional "always snap to server truth" call is
untouched, so D-11 holds exactly as before regardless of what is or isn't pending.

**Scope note on overlapping submissions** (added after plan-checker review of an earlier draft):
when two of this client's own moves are genuinely outstanding at once - a narrow window; D-11
itself documents only two real reconciliation sources (D-03 multi-tab, D-05 auto-pickup racing a
reconnect-move), neither of which is same-tab rapid double-dispatch - a broadcast that resolves
the *older* submission removes only that one entry from the tracker (FIFO, oldest first). The
still-genuinely-outstanding newer submission's own later broadcast is never silently marked
resolved by someone else's settlement, so a real divergence on it is never silently swallowed.
That is the guarantee this plan makes. It does **not** additionally guarantee zero false positives
in that same narrow window: because the mismatch check compares against the single current
`gameState` rather than a per-submission snapshot, the older submission's own broadcast can still
show the reconciliation toast even when that submission succeeded exactly as predicted, if the
newer submission's own optimistic prediction was still layered on top of local state at delivery
time. That is an accepted, deliberately-chosen trade-off - an occasional extra toast, never a
silently-missed rejection - not a defect this plan hides. Building true per-submission precision
would require retaining and diffing against each submission's own predicted state independently, a
materially larger change than a client-only tracking flag; out of scope here per this plan's own
client-only-fix boundary (no Edge Function or database change).

**Scope note on cross-player setup-phase races** (added after a second round of plan-checker
review): the safety argument above ("turn ownership already rules out a third source", D-11's own
framing) holds only for turn-gated moves in the `playing` phase (`PLAY_CARDS`/`PICK_UP_PILE`, both
turn-owner-checked in `applyMove.ts`). It does **not** hold for `READY_UP` or `SWAP_CARDS`: both
are gated only on `state.phase === 'setup'` (`applyReadyUp`/`applySwapCards`, `src/engine/
applyMove.ts` lines 258-261 and 295-302) with no turn-ownership check at all, by design - setup has
no turn concept, so any player may act independently of any other. Concretely: while this client's
own `READY_UP` is genuinely outstanding, a different player's own independent, unrelated
`READY_UP`/`SWAP_CARDS` broadcast can arrive first, mismatch this client's still-unconfirmed local
state, and fire the reconciliation toast even though this client's own move has not failed - it
simply hasn't resolved yet. `resolveOldestPendingMove()` then consumes this client's pending credit
anyway on that unrelated broadcast, so if this client's own move later did need genuine
reconciliation, that signal is now silently missed too (a false positive immediately followed by a
false negative). This is a second, narrower accepted residual, parallel to the same-client case
above: it requires near-simultaneous, cross-player, non-turn-gated setup-phase submissions
specifically, not "any move by anyone" (the original always-fires bug this plan closes). A fully
general fix would require correlating a broadcast to "was this specifically the resolution of my
own submission" - via either parsing the fragile `lastAction` string or a client-generated move ID
echoed back by the server - both of which mean touching the Edge Function/`apply-move` API
contract, outside this plan's client-only-fix boundary. Documented and tested (Task 2's cross-
player setup-phase test) rather than silently dropped.

In `GameContext.tsx`, add three pieces of state inside `GameProvider`, all private to this file

  - `pendingMoveCountRef = useRef(0)` - how many of this client's own submissions are currently
    unresolved.
  - `pendingMoveTimeoutsRef = useRef<Set<ReturnType<typeof setTimeout>>>(new Set())` - the
    safety-net timeout for every still-outstanding submission, tracked individually so one
    submission's resolution can never accidentally cancel another's timeout. A `Set`'s iteration
    order is insertion order, which this task relies on to identify "the oldest still-outstanding
    submission" without a separate ordered structure.
  - `beginPendingMove = useCallback((): (() => void) => { ... }, [])` - called once per real
    (non-test-mode) submission, immediately before the network call fires. Increments
    `pendingMoveCountRef.current`, schedules a `setTimeout` of `PENDING_MOVE_TIMEOUT_MS` that (if
    it ever fires) removes itself from `pendingMoveTimeoutsRef` and decrements the count (clamped
    at a floor of 0 via `Math.max(0, ...)`), adds that timeout to the set, and returns a `settle()`
    closure. `settle()` is idempotent: it only clears the timeout and decrements the count if this
    specific timeout is still present in the set (i.e. it hasn't already fired or already been
    settled once) - `pendingMoveTimeoutsRef.current.delete(timeoutId)` returning `true` is the
    guard. This per-call independence is what makes the "two overlapping submissions" behaviour
    correct: settling submission A can only ever cancel/decrement submission A's own entry, never
    submission B's.

Call sites for `settle()` are added in `useGameState.ts` (below), never here - `beginPendingMove`
only *creates* the tracking; it never assumes when or whether it resolves.

    actually accepted). Removes and clears **only the single oldest** entry still tracked in

| Boundary | Description |
|----------|--------------|
| Realtime broadcast → client reconciliation UI | Every subscribed client receives every accepted room write, including writes it did not itself submit; the pending-move gate decides which of those broadcasts is entitled to tell *this* client "your move didn't stick" |
